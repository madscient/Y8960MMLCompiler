## 目的と範囲

MML を書いたテキストファイルから、**Y8960 BASIC Extension の `MSAVE` が
書き出すのと同じ Y8SQ ブロック**と、**`EXPORT PCM` が書き出すのと同じ Y8PC
ファイル**を作るクロスコンパイラ。Windows / Linux / macOS。

- MML の仕様は Y8960 BASIC Extension と互換
- 出力の仕様は `Y8960BasicExtension/doc/bytecode.md` と `doc/pcmfile.md`
- **再生は範囲外。** 鳴らすのは Y8960Sequencer（`../Y8960Sequencer`）
- **GUI は範囲外。** 編集の場はエディタ拡張が受け持ち、それは別リポジトリ
  （下記「GUI を作らない」）

## 決定事項

### 開発言語は C++、ビルドは CMake

- 利用者の決定（2026-09-18）
- C++17、**CMake 3.18 以上**（当初は Y8960Sequencer と揃えて 3.20 だったが、
  下げた。下記）

#### どのプラットフォームで確かめたか

| | コンパイラ | CMake | 結果 |
|---|---|---|---|
| Windows 10 | MSVC 19.51 | 同梱 | ビルド・試験とも通る。警告 0 |
| Linux（WSL の Debian 11） | GCC 10.2.1 | 3.18.4 | ビルド・試験とも通る。`-Wall -Wextra` で警告 0（**要求を 3.18 に下げた写し**で確かめた。下記） |
| macOS | ―― | ―― | **未検証**。手元に環境が無い。公開して CI を置くまで確かめられない |

**Windows と Linux で出力がバイト単位で一致する**（確認済み ―― デモ曲と、
`presets/` の36本を `#pcmbank` で鳴らす曲の `.SQ` と `.PC` の3本を両方で作り、
SHA-1 を比べた）。パスの区切り、改行、バイナリの書き出しで差が出ていない。

**CMake の要求を 3.18 に下げた**（利用者の決定、2026-09-19）。3.20 のままだと
Debian 11（CMake 3.18.4）が構成の段で止まる（確認済み）。

- **下げても失うものは無い。** 3.18 に下げて構成もビルドも通った ――
  3.19 以降のコマンドは使っていない（使っていれば構成で止まる）
- `README.md` の試験の手順は `ctest --test-dir build`（ctest 3.20 の書き方）から
  `cd build && ctest` に直した
- **Y8960Sequencer とは要求がずれた。** 向こうは 3.20 のまま
- 3.19 以降の機能を使いたくなったら、この決定を読み直す

### 2層に分ける

| 層 | 中身 | 依存してよいもの |
|---|---|---|
| コア | ソースの読み込み、MML の解析、バイトコード生成、Y8SQ / Y8PC の書き出し | 標準ライブラリだけ |
| CLI | 引数の解釈、ファイル入出力、診断の表示 | コア |

- **前提**: コアが標準ライブラリだけで閉じていること。これが崩れると、

### GUI を作らない。編集の場はエディタ拡張で、それは別リポジトリ

- 利用者の決定（2026-09-18）。**当初の要件にあった「GUI に対応」をここで外した**
- **理由。** MML コンパイラの GUI は、中身が「テキストエディタ ＋ コンパイル
  ボタン ＋ エラー一覧」にしかならない。エディタを自前で作る労力に対して
  得るものが少なく、再生は Y8960Sequencer の担当なのでこのリポジトリの GUI は
  鳴らすこともできない
- **前例の観測**（確認済み ―― `../mml2mid64ide` を読んだ）。同じ形
  （MML コンパイラ ＋ VS Code 拡張）の先行プロジェクトがあり、上流へ出した要求は
  デバッグマップ・機械可読な診断・WASM ビルドの3つで、いずれも完了している
  （`docs/BACKEND-REQUIREMENTS.md`）。**拡張側は `docs/ROADMAP.md` の
  マイルストーン1 の項目4・5 が未着手のまま止まっている**（最終コミット
  2026-08-09、`extension/src` は 431行）。**1件の観測なので傾向とは言わない**が、
  値段がフロント側にあることは示している
- **別リポジトリにする理由。** 拡張は TypeScript / npm / VSIX という別の技術
  スタックと配布経路を持つ。同じリポジトリに入れると、C++ のビルドと CI に
  それが混ざる

#### 拡張との境界は CLI であって C++ の API ではない

別プロセス・別リポジトリになるので、**拡張が触るのは `y8mmlc` の引数・終了
コード・診断の書式**である。ここは今後「外から見える値」として扱う。

- いまの診断は `<パス>:<行>:<桁>: error: <文面>`（GCC と同じ並び）。
  **文面は振り直してよいが、この並びは動かすと拡張が壊れる**
- 終了コード: 0 が成功、1 がコンパイル失敗、2 が引数の誤り
  （**確認済み** ―― 4通りを走らせて `$?` を見た）
- **stdout と stderr は UTF-8**（2026-09-19 から。それまで Windows では ANSI
  コードページと UTF-8 が1行の中で混ざっていた）。下記「Windows でも文字は UTF-8」
- **y8mmlc 自身の言葉（診断の文面、使い方、警告）は英語で、ASCII に収める**
  （利用者の決定、2026-09-19）。どのコンソールでも化けないように。引用する
  利用者の文字列（パス、ソースの抜き出し、`#define` の名前、ADPCM のエントリ名）
  は UTF-8 のまま出す ―― 拡張が診断のパスからファイルを開けるように
  - **崩れたら試験が落ちる**（`tests/ascii_test.cpp`）。`src/` のうちコメントで
    ない部分に ASCII でない文字があると落ちる。**コメントは日本語で書いてよい**
    （利用者）。確認済み ―― 文面に日本語を1つ入れると、その行を示して落ちた
- **`--diag=json` はまだ無い。** 足すかどうかは未決（下記）

#### Windows でも文字は UTF-8

拡張のリポジトリからの依頼で直した。方針は利用者の決定（2026-09-19）。

**起きていたこと**（確認済み ―― 直す前に再現した）。Windows の CRT は `argv` を
ANSI コードページで作り、狭い文字のパスも ANSI として開く。ソースは UTF-8 なので、

- `#pcmbank` のパスに日本語があると開けなかった（UTF-8 のバイト列を ANSI として
  読む）
- ANSI コードページで書けない文字を含むパスを引数に渡すと、`?` に化けて開け
  なかった
- 診断の1行の中で、パスは CP932、引用したソースの文字列は UTF-8 になっていた

**直し方。** `wmain` とワイド文字のパスに書き換える案は採らなかった（変える量が
多い。利用者の決定）。

- 実行ファイルに `activeCodePage` を UTF-8 にするマニフェストを埋め込む
  （`src/cli/y8mmlc.manifest`）。プロセスのコードページが UTF-8 になり、`argv`・
  `std::ifstream` のパス・書き出しがソースと同じ UTF-8 で揃う。コアは変えていない
- 標準出力か標準エラーがコンソールのときだけ、コンソールの出力コードページを
  UTF-8 にし、終わるときに元へ戻す（`ConsoleUtf8`）。パイプやファイルには
  バイトがそのまま流れるので触らない
- **マニフェストは実行ファイルにしか効かない。** だから試験（`tests/cli_test.cpp`）は
  コアを同じプロセスで呼ばず、`y8mmlc` を子プロセスとして起動する

**確かめたこと。**
- **確認済み** ―― 出来た実行ファイルに `<activeCodePage>UTF-8</activeCodePage>` が
  入っている。`cli_test` は直す前に6か所すべてが落ち、直した後は通る（Windows・
  Debian とも）。手で再現した3件も直った
- **推測** ―― 効くのは Windows 10 バージョン 1903 以降。根拠は Microsoft の
  `activeCodePage` の説明で、それより古い Windows では試していない。古い Windows
  では今までの挙動（ANSI）のまま動く
- **推測** ―― コンソールの出力コードページはプロセスが終わっても残る。元に戻す
  ようにしたので、残るかどうかによらず結果は同じ
- **未検証** ―― コンソール（`chcp 932` の cmd）で日本語の診断が化けずに表示される
  こと。ここではコンソールを持たない環境でしか走らせていないので、`ConsoleUtf8` の
  経路は通っていない

#### 出力名の ASCII でない文字は、1文字を `_` 1つにする

利用者の決定（2026-09-19）。`曲1.mml` → `_1.SQ`。UTF-8 のバイト数ではなく文字を
数えるので、文字コードによらず同じ名前になる（それまでは Windows で CP932 の
バイト数だけ `_` が並び、UTF-8 に揃えると `___` になるところだった）。
**置き換えたときは警告を出す** ―― `曲.mml` と `歌.mml` がどちらも `_.SQ` になるのに
気づけるように。形の崩れた UTF-8 のバイトは、1バイトを1文字として数える

### TextMate 文法（構文強調）はこのリポジトリに置く

`syntaxes/y8960mml.tmLanguage.json`。利用者の決定（2026-09-19）。一度は拡張の
リポジトリに置くとしたが、改めた。**拡張がこれをどう受け取るか（submodule、
写す、リリースから取る）は拡張のリポジトリが決める**（利用者）。

- **文法が写し取る仕様は、ここで変わる。** 行の種類、メタコマンド、`\` の行連結、
  MML のコマンドを決めているのは `source.cpp` / `mml.cpp` と `mml-source.md`・
  `mml-reference.md`。
  同じコミットで直せる
- **ずれたら試験が落ちる。** メタコマンドはパーサの表 `kMetaCommands`
  （`source.cpp`）1箇所にまとめ、`tests/grammar_test.cpp` が文法の
  `meta-command` 規則と突き合わせる。デバイスのシンボルも同じく
  `device-symbol` 規則とデバイス表を突き合わせる。**両方向**で見るので、
  文法だけにある名前も落ちる（確認済み ―― 文法から `adpcm` を外すと、
  食い違った名前を挙げて落ちた）
- **MML のコマンド文字は突き合わせていない。** `mml.cpp` の振り分けは表に
  なっておらず、文法の側も文字の集合で書いている。足したら両方を手で直す
- 別リポジトリにした理由（TypeScript / npm / VSIX を持ち込まない）とは
  ぶつからない。文法は JSON のデータ1本

**外から見える値。** 置き場所 `syntaxes/y8960mml.tmLanguage.json` と
`scopeName` の `source.y8960mml` は、拡張の `package.json` が参照する。変えるなら
ファイル名と `scopeName`、`grammar_test.cpp` の期待値、`CMakeLists.txt` の
パス、それに拡張のリポジトリの参照が動く。

**どこまで確かめたか。**
- **確認済み**（Oniguruma ―― VS Code と同じ正規表現エンジン ―― を scratchpad
  に入れて試した）。全部の正規表現がコンパイルできる。VS Code と同じく行の末尾に
  改行を足して流す簡易トークナイザで、31 か所の scope が期待どおりになり、
  `examples/demo.mml` に invalid になるトークンが無い。行連結でコメントや
  メタコマンドが次の行へ続くこと、`\` の後ろの空白があっても続くことを含む
- **未検証** ―― VS Code 本体（vscode-textmate）では色付けしていない。簡易
  トークナイザは vscode-textmate の規則のうち、この文法が使う部分だけを
  まねたもの。拡張のリポジトリで確かめることになる

**制約。** リズム音用 MML のトラックも普通の MML として色が付く。どのトラックが
リズムかは `#assign` のチャンネルで決まり、TextMate 文法はそれを見られない。
`#define` の `"..."` の中身（MML）も、ただの文字列として色が付く

### コマンド名は `y8mmlc`、第1引数が MML ソース

```
y8mmlc <MML ソース> [-o <基底名>] [--out-dir <フォルダ>]
```

- コマンド名は要件で与えられている
- ソースは UTF-8。BOM は付いていても読む

### 出力は MSX-DOS の 8.3 に合わせ、`.SQ` と `.PC` にする

- 利用者の決定（2026-09-18）
- `song.mml` → `SONG.SQ`（Y8SQ）と `SONG.PC`（Y8PC）
- 基底名は入力の茎を大文字にしたもの。**8文字を超えるときは切り詰めて警告を
  出す** ―― 黙って切ると、別の曲が同じ名前になったことに気づけない
- `-o` は基底名を取る。拡張子を書いても捨てる。ここでも8文字を超えれば警告
- **`.PC` は `#pcmbank` を書いたソースにだけ出る。** ADPCM を使わない曲に空の
  ファイルを作らない
- **前提**: 出力を MSX へ持っていく経路が、名前をそのまま使えること。PC 上で
  だけ扱うなら長い名前のほうが読みやすいが、持ち込みのたびに改名するほうが高い

### MML ソースの形式

詳細は [`mml-source.md`](mml-source.md) が正。ここには**なぜそうしたか**だけ置く。

#### 1ファイル ＝ 1シーケンス

- Y8SQ ブロックはシーケンス1本ぶんの形（`bytecode.md`「ブロック」）で、
  `MSAVE` もシーケンス1本を書き出す。トラック名 `A`-`P` が 16 トラックに
  ちょうど対応する
- シーケンス番号を書く場所を作らないので、**メタコマンドにシーケンスの概念が
  出てこない**

#### トラック行は同じトラック名を何行でも書ける。連結される

- ROM の `MTRK` を分けて呼ぶのと同じ
- **ただしループ・ブロック・連符が閉じる単位はファイル全体**にした。ROM は
  `MTRK` 1回の中で閉じることを求めるが、そちらは「まだ書かれていない `MTRK`」
  を指せないという BASIC 側の都合で、ファイルにはその都合が無い
- **流用元との差。** ROM で通るものは通り、ROM で落ちるものが通る側の差なので、
  同じソースが同じバイト列になる関係は保たれる

#### 変数参照 `=x;` `Xx;` は、ファイル内のマクロとして再解釈する

- 利用者の決定（2026-09-18）。PC 側に BASIC の変数は無い
- `#define <名前> <数値>` を `=名前;` が、`#define <名前> "<MML>"` を
  `X名前;` が参照する
- **連鎖は 8 本まで**（ROM の `XCHAIN_MAX` と同じ）。自分を指す定義で
  終わらなくなるのを止めるため
- **流用元との差2つ。** どちらも ROM で落ちるものが通る側
  - **`X名前;` の後にも MML を書ける。** ROM が禁じているのは、変数の文字列を
    読み終わったあと元の位置へ戻る手段を持たないため。ファイルなら戻れる
  - **名前は英字で始まる英数字と `_`。** BASIC の変数名の規則に縛られない

#### 行の末尾の `\` で次の行を連結する

- 利用者の決定（2026-09-18）
- **行の種類を見る前につなげる。** だから `\` はメタコマンドにもトラック行にも
  コメント行にも効き、規則が1つで済む。値段は、**コメント行を `\` で終えると
  次の行もコメントになる**こと。文書に書いた
- `\` の後ろの空白は無視する。見えない末尾の空白で連結が切れると、
  切れた理由が読み手に見えないため
- 診断は**物理行**を指す。連結した行の何行目で誤ったかが分かる

#### ADPCM は `#pcmbank` が読み、バンクが自分で番号を付ける

- 利用者の決定（2026-09-18）
- `#pcmbank <JSON のパス>` が adpcm_packer の出力（`.json` と、同じ茎の `.bin`）
  を指す。**読んだ時点でボイスファイルの表が組める**ので、`entries` の先頭から
  64 個が番号 0-63 を取り、**`#adpcm` が1つも無くても `@`*n* が鳴る**
- **番号の上限は `pcmfile.md` が決める。** コードは `kPcmVoiceMax` 1箇所を見て
  いて、範囲の文面もそこから組み立てる ―― 数を2箇所に書くと片方が古くなる
- **曲とサンプルの対応が MML ソースの中で閉じる。** ビルドのコマンドに覚えて
  おくことが無くなる
- **`#voice` は音色定義に譲った**（利用者の決定、2026-09-18）。数値域
  （ADPCM 0-31、FM 音色 128-191）は重ならないので1つのコマンドで両立はできたが、
  同じ名前が2つの意味を持つ形を避けた。`VOICE COPY` と名前が揃うのは音色側

##### `#adpcm` は既定の番号への「追加」であって「移動」ではない

- 利用者の決定（2026-09-18）
- `#adpcm <番号 0-63> <エントリ名>` は、**その番号をそのエントリにする**だけ。
  既定で付いた番号は消えない。`#adpcm 10 bassdrum` と書くと bassdrum は
  0 番でも 10 番でも鳴り、Y8PC の設定は2件になる（同じページを指す2件は
  `pcmfile.md` が認めている）
- **規則が1行で済む**ほうを採った。「移動」にすると、既定の番号から外す処理と、
  外れて空いた番号の扱いが増える
- 番号を名前で固定したいのは、バンクにサンプルを足したときに番号を動かしたく
  ない場合。**そのときは使うものを全部 `#adpcm` で書く**ので、追加か移動かの
  差は出ない

### バイトコードの仕様は `bytecode.md` が正。ROM のコードは隅を決めるときだけ読む

- **仕様とコードが食い違うときは仕様に合わせる。** Y8960Sequencer と同じ方針
  （向こうの `doc/plan.md`）。ROM 側は不具合として直っている
- 仕様が名前を付けていない隅（音長の端数、付点の重ね方、連符の割り前）は
  ROM のコードを読んで合わせる。**読んだ箇所と読み取った規則をここに記録する**

#### 読み取った規則

**確認済み**（`../Y8960BasicExtension/src/mml/lexer.asm` の `GETLEN` /
`GETLENDOT` / `GETLENDEF`、`src/mml/parse.asm` の `CM_LENGTH` /
`CM_TUPSTART` を読んだ。**走らせてはいない**）。

- **音長の tick は `192 / n` の切り捨て。** 端数の繰り越しは無い。MsxMusic の
  MML が持つ「端数は次の音符へ繰り越される」は、この ROM には入っていない
- **付点は、基準を `d` として `d >>= 1; 合計 += d` を付点の数だけ繰り返す。**
  `R4.` は 48 ＋ 24 ＝ 72。`n` が小さいと `d` が 0 になり、それ以上は増えない
- **連符の割り前は `GETLEN` の結果を音符の数で割った切り捨て。** 割り前が
  2 tick 未満なら `Illegal function call`（`音符数 × n > 96` と同じ条件）
- **連符長にも付点を書ける**（`{CDE}4.`）。ROM が `GETLEN` をそのまま使った結果
- **数えるのは音符の文字と `N`*n* と `R`*n* だけ。** `&` と `@W`*n* は時間を
  取るが数に入らない

**確認済み**（`../Y8960BasicExtension/doc/plan.md` 段階6 が持つ、フォークの
openMSX で取った実例を読んだ。**こちらで走らせてはいない**）。回帰試験の
期待値にそのまま使う。

| MML | バイト列 |
|---|---|
| `L8CDE` | `00 18 02 18 04 18 FF` |
| `{CDE}4` | `00 10 02 10 04 10 FF` |
| `{C8DE}4` | `00 18 02 10 04 10 FF` |

- **`T120@1V15O3Q4A1` の実例（`84 78 82 01 …`）は段階6 のもので、そのままでは
  使えない。** 段階14 で FM の `@1` は `85` ＋ 音色集合の索引になった。
  `84 78`・`81 7F`・`80 03`・`83 04`・`09 80 C0` の部分は変わっていない

#### ROM のコードが仕様と食い違っていた箇所

**方針どおり仕様に合わせた。** どれもこちらが ROM より厳しい側に倒れるので、
ROM が受け付ける MML の一部をこちらが断っていた。コードを読んで気づいたもの。
**いまは ROM の側も直っている**（下記）。

- **`(TC)` が2つ以上あって `(CODA)` が1つも無いトラック。** ROM は待ち行列を
  排出する場所（`PARCODA`）を通らないので、2つ目以降の飛び先に**鎖のリンク
  （直前のフィールドの位置）が残る**。仕様は「0 なら無視」なので、こちらは
  全部 0 を書く（`../Y8960BasicExtension/src/mml/loop.asm` の `PARTC` と
  `PARCODA`、`src/inc/memmap.inc` の `CMPL_CODA`）
- **長さ 0 の `N`*n* が2つ続く形。** ROM の `CM_NOTEABS` は `CMPF_NOTIME` を
  見ない（`NOTEMIT` だけが見る）ので通ってしまう。仕様は「長さ 0 の音符のあと、
  次の音符までに時間を進めるものを挟まないと `Illegal function call`」なので、
  こちらは `N`*n* でも断る（`src/mml/parse.asm` の `CM_NOTEABS`）
- **ADPCM チャンネルの `@`*n* が 64 以上。** ROM の `CHKVOICE` は FM 系の範囲
  （0-191）で見るだけで、ADPCM かどうかを知らない。仕様は 0-63 なので、
  こちらは 64 以上を断る（`src/mml/parse.asm` の `CHKVOICE` と `VOIKIND`）
- **`Y` の音源ごとのレジスタ範囲**（2026-09-19、利用者の決定）。
  `basic-reference.md` は「範囲外を書くと `Illegal function call`」と書くが、
  **確認済み**（コミット済みの `b38acbe` を読んだ）―― ROM の `CM_REG` は
  255 以下かどうかしか見ない。範囲の検査は演奏するときに各ドライバ
  （`OPL2CHKREG`・`DCSGCHKREG` など）が行い、断られた書き込みはシーケンサの
  `TRKEV_REG` が黙って捨てる。つまり OPL2EX の `$04` も ROM では書かれない。
  こちらは文書どおりコンパイルのときに断る（`mml.cpp` の `cmdReg`）
  - **ROM の振る舞いを書くときは、`basic-reference.md` ではなくコードを読んで
    から書く。** この件のように、ROM の文書とコードが食い違っていることがある

**ROM の `10cc834` で4件とも解消した**（2026-09-19。利用者が ROM に伝えた）。
**確認済み**（ROM の `doc/plan.md` の「課題 ― 仕様と食い違う4件を仕様に
合わせる」と、`src/mml/loop.asm`・`parse.asm` を読んだ）―― **4件とも ROM が
コードを仕様に合わせた。** 仕様の側は変わっていないので、こちらのコンパイラは
変えていない。ROM の試験が見ている境界（`Y` の範囲の両端、ADPCM の `@63` と
`@64`）はこちらの試験と同じ。ROM の試験が記録したバイト列
（`N60=Z;R4N62=Z;` → `C0 3C 00 0C 30 C0 3E 00 FF`）を回帰試験の期待値に足した

#### セーニョは目印 `86` を出す

ROM の `10cc834` で仕様が変わった（`bytecode.md` のイベント表に `86`）。ROM では
`(TC)`/`(CODA)` と `(DS)`/`(*)` を、別の `MTRK` に書いても対にするためのもの
（トラックの中から飛び先を探せるように、目印を残す）。

- `(*)`*n* は `86 n` を出す。演奏では何もしない
- `(DS)`*n* は、それより前にある同じ番号の `86 n` のうち**最後のもの**の、
  **目印の直後**へ飛ぶ。無ければ距離 0
- `(TC)` は `(CODA)` の `44` の直後へ飛ぶ。コーダがまだ無ければ 0 を書き、
  `(CODA)` が来たら埋める ―― こちらはもとからこの作り

**このコンパイラはファイル全体を1回で解析するので、`MTRK` をまたぐ問題は
もともと無い。** 変えたのは `86` を出すことだけ。確認済み ―― 直す前に、新しい
期待値の試験3件（1つのセーニョ、同じ番号が2つ、番号で選ぶ）が落ち、直した後に
通った。`86` を含むブロックを Y8960Sequencer の `y8960player` が読み込んだ
（鳴らしてはいない）

#### `C-` と `B+` は音符オペコード `0F` `10` を出す

ROM の `8267eb1` で仕様が変わった（`bytecode.md` のイベント表と、その上の
音の高さの段落）。それまでは同じオクターブの中で折り返していた（`O4C-` が
`O4B`）。

- `c-` は `0F`（1つ下のオクターブの b）、`b+` は `10`（1つ上のオクターブの c）を
  出す。**走行状態のオクターブは動かさない。** ほかの臨時記号は今までどおり
  `00`-`0B`
- `O8` の `B+` を断らない。ROM の `ACCID`（`src/mml/parse.asm`）も断らないので
  それに合わせた。**未検証** ―― 演奏すると音符番号が 108 になり、`N` の上限
  （96）を超える。チップに何が書かれるかは確かめていない
- `O1` の `C-` は音符番号 11 で、範囲内。ROM が番号 −1 を 0 に丸めるのは、
  ループの中の `<` で演奏時のオクターブが 0 まで下がったときだけ
- 上の2項は ROM の `ae83e5d` より前の記述。オクターブが 0-9 になったので、
  `O8` の `B+` はもう端ではない（`O9` の `B+` は音符番号 132 で `C0` の上限 139 の内）

#### オクターブは 0-9、`N` は 0-127 で O1 C から数える

ROM の `ae83e5d` で仕様が変わった（`bytecode.md` のイベント表の `80` `C0` と
「上限」、`basic-reference.md` の「`O`*n*」「`N`*n*」「出せない高さ」）。

- `O`*n* は 0-9。`<` は O0、`>` は O9 で止まり、エラーにもイベントにもしない
- **`N`*n* の数え方が変わった。** `N0` が O1 C（MMBE と同じ）で、`C0` のオペランドは
  *n* ＋ 12。**同じ `N` を書いた既存の MML は1オクターブ下で鳴るようになる**
  （以前は `N48` が O4 C、いまは `N36`）。ROM に合わせるのでこちらに選択肢は無い
- 確認済み ―― ROM の `mtrk.tcl` が見ている `N60` `N62` → `C0 48` `C0 4A` を
  回帰試験の期待値に写した（以前の `C0 3C` `C0 3E` を置き換えた）。境界の
  O0・O9・`N0`・`N127` を踏み、直す前に落ちることを確かめた

#### ソフトウェアエンベロープ `@E`*n* と `#env`

ROM の `1dc7618` で入った（`bytecode.md` の `B2`・チャンク `04`・「上限」、
`basic-reference.md` の「ソフトウェアエンベロープ」）。

- **定義は `#env <番号 1-31> <AR>,<DR>,<SL>,<RR>`**（利用者の決定、2026-09-27）。
  `#voice` `#wave` と同じくカンマで並べる
- **`#env` の無い番号を SSGS・SCC・DCSG のトラックで `@E` に書くとエラー**
  （利用者の決定、2026-09-27）。`#voice` `#wave` の未定義と同じ扱い。BASIC は
  共有の表の中身を写すが、コンパイラには写す表が無い
- **4つの値は 0-255 を通し、範囲は検査しない**（利用者の決定、2026-09-27）。
  ROM の `ENV COPY` と同じ。負の数と `"..."` は受けない（`#voice` とはここが違う）
- **FM・ADPCM・リズムのトラックの `@E` は読んで捨てる。** 番号の範囲（0-31）だけは
  見る ―― ROM の `CM_ATENV` が範囲を先に見てからデバイスを見るので、`@E32` は
  どのトラックでもエラー。未定義の番号も FM 側では断らない（何も書かないので）
- **チャンク `04` はチャンク `03` の後ろに、番号の順で置く。** 並び順には意味が
  無い（`bytecode.md`）。名指されない `#env` は書かない
- **連符の中の `@E` の `e` は音符として数える。** ROM の `ISNOTECH` は文字だけを
  見て a-g・n・r を数える（確認済み ―― `src/mml/parse.asm` の `TUPCOUNT` を読んだ）。
  こちらの `tupletCount` も同じ規則なので、揃えたままにした。`{@E1CDE}4` は
  4つに割る
- 前提: 値の検査を ROM が始めたら、`#env` の検査を読み直す。値段は `doEnv` の
  1か所と試験・文書
- **確認済み**（2026-09-28）―― Y8960Sequencer の `bb40405` 以降のビルドの
  `y8960player` がチャンク `04` を持つブロックを受理し、`@E1` の有無で WAV が
  変わった。対応したのは v0.1.4 で、それより前の公開版が拒むかは確かめていない
  （`bytecode.md` の規則では、種別 `7F` 以下の知らないチャンクはブロック全体を

#### リズム音用 MML の長さ 0・`@W`・楽器ごとの音量

ROM の `84e52e1` と `0b40308` で入った（`basic-reference.md` の「リズム音用
MML」、`bytecode.md` の `D8`）。依頼文書は無く、両コミットの文書とコードの差分を
読んで追従した。

- **長さ 0 の打撃**（`B0`）。時間を取らない打撃のあと、時間を進めずに次を打つと
  エラー（`R0` も `@W0` も時間を進めない）。ROM の `RHYINST3` が `CMPF_NOTIME` を
  見るのと同じ。音符と同じ `noTime_` を使う
- **`@W` がリズムトラックでも使える。** ふつうの MML と同じ処理（`cmdWait` に
  まとめた）
- **`@B` `@S` `@M` `@C` `@H`**（0-15）は `D8` ＋ 楽器1つのビット ＋ 値。`V` と
  `@V` は今までどおり `A9`。範囲外・数なし・楽器でない文字はエラー（ROM の
  `rhyinst.tcl` が断る3件と同じ）
- **シーケンス音量の減算と SCC の音量表は再生側の変更**で、コンパイラの出力は
  変わらない。SCC の表は利用者向けに `mml-reference.md` の `V` の節へ写した
- 確認済み ―― ROM の `rhyzero.tcl` が記録したバイト列（`T60B0@W1H1` →
  `84 3C A8 00 C8 10 00 0E 80 C0 C8 01 80 C0 FF`）と、断る3件（`B0H1`、`B0R0H1`、
  `B0@W0H1`）を回帰試験に写した。`D8` のバイト列は ROM の試験に無いので、
  `bytecode.md` から組んだ。**直す前のコードで、正の側の4件が落ちるのを見た。**
  断る側は直す前も通っていた（`@W` と `@B` をまるごと断っていたため）ので、
  境界の内側（`@B15`・`@S0`、`B0@W8H8`）が通る試験を足した
- 逆コンパイラ: `D8` は楽器ごとの `@B` などに戻す（ビットが複数なら1つずつ）。
  リズムの `0E` は休符ではなく `@W` に、書けない長さの打撃の残りも `@W` に
  した。これで「ROM でもリズムの休符が何もしないか」という未確認の前提に
  頼らなくなった

### JSON は自前で読む

adpcm_packer の JSON を読むのに nlohmann/json を FetchContent で取る案があったが、
**コアは標準ライブラリだけに依存する**という決定のほうを採った
（`src/core/json.cpp`、約250行）。

- 設定時にネットワークが要らない。オフラインでビルドできる
- 読むのは1つのスキーマだけで、そこに要る JSON は全部揃っている
- 値段: 入力の形が増えたらこちらが直す。**JSON の仕様のうち使っていないのは、
  サロゲートペアを1つの符号位置に畳むことだけ**（名前に絵文字を書くと壊れる）

### 診断は行と桁を持つ。1回の実行で全部を出すことは求めない

- ROM は `Illegal function call` の1種類しか返せないが、**PC にはその制約が
  無い。** どこが悪いかを言えるなら言う
- **同じ段の中では最初の1件で止めない。** トラックごとに解析するので、
  あるトラックの誤りは他のトラックの解析を妨げない。メタコマンドも1行ずつ見る
- **段をまたいでは続かない。それでよい**（利用者の決定、2026-09-19）。
  ソースの読み込み（メタコマンドとトラック行の振り分け）に誤りがあると、
  MML の解析に進まずに返る（`compileText` / `compileFile`）。確認済み ――
  メタコマンドの誤りと MML の誤りを1つずつ持つソースで、報告されたのは
  メタコマンドの1件だけだった
  - 値段: 全部を出すことにするなら、読み込みの誤りがあっても `#assign` が
    通ったトラックは解析する形になる。`compile.cpp` の2箇所と試験1本
- **前提**: 診断の文言は外に出る値だが、**振り直しても波及しない**（文言だけが
  動く）。だから着手前に決めない

### Y8SQ から MML ソースへの逆コンパイル `y8mmld`

2026-09-27 に実現可否を検討してから、次のとおり決めて作った（利用者の決定、
2026-09-27）。検討の中身は下に材料として残す。

- **目標は「鳴り方が同じ」。バイト列は2往復目から変わらなければよい。**
  Y8SQ₀ を逆コンパイルした MML₁、それをコンパイルした Y8SQ₁、それを逆コンパイル
  した MML₂、…について、**MML₂ ＝ MML₁ かつ Y8SQ₂ ＝ Y8SQ₁**（テキストとバイト列の
  一致）。Y8SQ₀ と Y8SQ₁ は一致しなくてよい
  - だから長さは MML の拡張ではなく、**タイと休符に分けて書く**（障害1）。分けた
    結果の Y8SQ₁ は音符がどれも1つで書ける長さになっているので、2周目では分ける
    ものが無く、そのまま戻る
  - 前提: 逆コンパイルが、1つで書ける長さの音符をそのまま1つの音符に書くこと。
    これが崩れると2周目以降も形が動く
  - 試験: 往復の一致は既存の試験の MML から作れる。鳴り方の一致は、
    `../Y8960Sequencer` の `y8960player --wav` で Y8SQ₀ と Y8SQ₁ を WAV にして
    比べられる。分けたタイの音符が同じ F-Number を書き直しても WAV はビット単位で
    一致した（下の「確かめたこと」）
- **ADPCM は「ろ」: `#pcmbank` が Y8PC も読む**（障害2）。逆コンパイルした MML は
  `#pcmbank <Y8PC のパス>` を書く。Y8PC はそのまま写すので往復で変わらない
  - 前提: Y8PC の形（`pcmfile.md`）が、ボイスファイルの設定を番号つきで持つこと
  - 利用者向けの文書は `mml-source.md` の `#pcmbank` に書いた

- **別コマンド `y8mmld`**（利用者の決定、2026-09-27）。入力と出力の向きが
  逆で、オプションの意味も変わるため。コアは `y8mmlc_core` を共有する
  - 出力は **`<入力の茎>.mml` を入力と同じ所に**。`-o <ファイル名>` と
    `--out-dir <フォルダ>` で変えられる。`-o` は名前だけを変え、置き場所は
    `y8mmlc` の `-o` と同じく入力の所（`--out-dir` があればそこ）
  - **出力が既にあれば断る。`--force` で上書き。** `song.mml` から作った
    `SONG.SQ` を逆コンパイルすると、大文字小文字を区別しないファイルシステムでは
    手書きのソースを平たい MML で消してしまうため
  - **Y8PC は同じ茎の `.PC` を自動で使う。`--pcm <ファイル>` で別のものを指定
    できる。** `y8mmlc` が `SONG.SQ` と `SONG.PC` を組で出すので、そのまま戻せる
  - 値段: 名前を変えるなら CMake の標的名、README、CLI の試験

#### 何を「逆コンパイルできた」とみなすか

目標の強さで答えが変わる。

| | 対象 | 求めること |
|---|---|---|
| 甲 | `y8mmlc` の出力 | 逆コンパイルした MML を `y8mmlc` に通すと**同じバイト列**に戻る |
| 乙 | ROM の `MSAVE` の出力 | 同上。無理なら同じ鳴り方 |
| 丙 | Y8960SeqConverter の出力（OPLLDRV・MuSICA 由来） | 同じ鳴り方 |

**甲は検証の手段が安い。** 既存の試験の MML を全部「コンパイル → 逆コンパイル →
コンパイル」してバイト列を突き合わせれば、それが回帰試験になる。

#### 失われて、戻らなくてよいもの

`#define` と `=x;` `Xx;`、`L`*n*、連符 `{ }`、コメント、`\` による連結、
`+` と `#` の別、`V` と `@V` の別（`81` の値が `n*8+7` なら `V` で書ける）。
どれもバイト列に跡を残さない。逆コンパイルした MML は元の書き方には戻らず、
**音符ごとに長さを書いた平たい MML** になる。

**プリセット音色の番号も失われてよい**（利用者の判断、2026-09-27）。`85` の
索引が指すレコードは全部 `#voice`（128-191）と `#wave`（16-31）の定義として
書き出せばよく、同梱のプリセット表と突き合わせる処理が要らない。
- 前提: 1シーケンスの音色集合は 32 本。FM 音色は `#voice` の 64 個に必ず収まる
- **SCC の波形が 17 本以上あると `#wave` の 16 個に収まらない。** 推測 ――
  `y8mmlc` と ROM は波形を `@0`-`@31` からしか作れず、ユーザ域は 16 個なので
  そういうブロックは両者からは出てこない。出てきたら、その分だけプリセット表と
  突き合わせる

#### 素直に戻るもの

イベントと MML がほぼ 1対1 のもの。`00`-`0B` `0F` `10`（音符、`c-` `b+`）、
`0C` `0E`（`R` `@W`）、`40` `41` `80`、`81`、`83`、`84`、`86`、`C0`（`N`、12 を引く）、
`D0` `D1` `D2`、`E0`、`45`、`42`/`E2`、`43`、`44`、`B0` `B1` `B2` `DC`、`A9` `AA` `C8`、
トラックのチャンク（`#assign`）、チャンク `04`（`#env`）。

ループ・ブロック・トゥコーダ・ダルセーニョは距離を持つので、**距離から対応を組み
直す**必要がある。`y8mmlc` の出力なら入れ子が正しいので組み直せる。
`mml.cpp` の `cmdLoopEnd`・`cmdBlockStart`・`blockClose`・`cmdParen` を読んで、
どの距離がどこを指すかを確かめてから組み直しを書いた。`y8mmlc` の出力で戻ることは
下の「確かめたこと」。

#### 障害1: 音長。MML は任意の tick 数を書けない

**確認済み**（`getLen`・`dots` の規則を Python で写し、0-336 tick を数えた）。

- 音符1つに長さを書く形（`192 / n` の切り捨て、付点）で書けないのは、0-336 の
  337 通りのうち **266 通り**。1 tick もここに入る
- 連符の割り前（`{ }` に何音か入れる）を使っても **155 通り**残る。しかも
  連符で出すには、前後の音符をまとめて1つの連符に入れる組み合わせを探すことになる
- **甲と乙では原理的には戻る。** そのバイト列はもともと MML から出たので、
  書き方が必ず存在する。ただし連符の組み直しは探索になり、実装が重い
- **丙は1つの音符では書けない。** Y8960SeqConverter は 1 tick ＝ 1/60 秒で、
  1つのイベントに 8191 tick まで書く（`../Y8960SeqConverter/doc/conversion.md`
  「時間」）。MML の長さの上限（全音符の付点）を超える。分けて書く方法は下

**タイと休符に分ければ、MML の拡張なしで鳴り方を保てる**（利用者の案、2026-09-27）。
ただしバイト列は変わる（`45` と `83` が増える）ので、甲の「同じバイト列」には
使えない。鳴り方を保つ目標なら使える。

- **確認済み**（`../Y8960Sequencer/src/core/sequencer.cpp` の `setGate` を読み、
  その規則を Python で写して 1-8191 tick を数えた）。ゲートは
  `max(1, (音長 × Q) >> 3)`。**タイだけで分けると `Q` が 1-7 の音符はほぼ全部
  崩れる** ―― つないだ前半はゲートを持たないので、キーオフが最後の1片の中でしか
  起きず、元のキーオフの位置（音長の Q/8）に届かない
- **鳴る部分と黙る部分に分けて書けば崩れない。** 音長 T、Q が q の音符は、
  G ＝ `max(1, (T × q) >> 3)` だけ鳴って T − G 黙る。これを
  `Q8` ＋ G をタイでつないだ音符 ＋ T − G の休符 ＋ `Q`q と書く。
  **書けないのは 1 tick の片が出るときだけ**で、1-8191 tick・Q1-8 のうち、単独の
  音符で書けないものに限ると **T ＝ 1 だけ**が残る（2 以上は 2 と 3 の和で必ず書ける）
- 音符の直後が `45` か `D2 8000h` のとき（つながる音符）は Q が効かないので、
  タイでつなぐだけでよい
- **休符と `@W` は分けて書くだけでよい**（休符はキーオフしてから待つので、重ねても
  同じ。`0E` はキーに触らない）
- **リズムの打撃（`C8`）は、打撃 ＋ `@W` に分けられる。** リズムトラックには `&` が
  無いが、ROM の `84e52e1` から `@W` が使える（`B0@W8` は `B8` と同じ）
- **崩れるもの: ポルタメント。** `~` は次の音符1つの長さで距離を閉じ、ポルタメントの
  付かない音符は走っているポルタメントを終わらせる（`bytecode.md`）。分けると
  最初の1片で閉じ、以後はタイの音符で打ち切られる。**`~` の付いた書けない長さの
  音符は鳴り方が変わる。** 推測 ―― Y8960SeqConverter の出力に `D2` が出るかは
  見ていない
- **残る障害は 1 tick の音符・打撃。** 1/60 秒の音符が元データにあれば出る。
  出るかどうかは実物を見ていない

**tick 数をそのまま書く長さ（他の MML 方言の `%`*n* のような形）を MML に足す案は
見送った。** 理由: 目標が「鳴り方が同じ」と「2往復目から変わらない」になり、
Y8SQ₀ とバイト列まで同じにする必要が無くなった。足せば1往復目からバイト列が
同じになり、1 tick の音符と `~` の付いた音符も書けるようになる。この2つが実物で
問題になったら読み直す。
**2026-09-27 に読み直す条件に当たったが、見送りのままにした**（利用者の判断、
2026-09-28。聴いてほとんど分からないため）。調べた結果は下の「Y8960SeqConverter の
出力で確かめたこと」。

#### 障害2: ADPCM のサンプルはブロックに無い

チャンク `03` が持つのはサンプルメモリ上の置き場所と周波数だけ。
**Y8PC を同時に渡させれば解ける**（利用者の案、2026-09-27）。Y8PC はボイスファイル
ごとの設定（チャンク `03` と同じ7バイト）とサンプルメモリのダンプを持つので、
中身は足りている。

問題は `#pcmbank` が **adpcm_packer の JSON と `.bin`** しか読まないこと。
**確認済み**（`adpcm.cpp` の `readAdpcm` を読んだ）。求めるのは `codec` が
`adpcm-b`、`boundary` が 256、最上位の `sample_rate`、`entries` の `name` `offset`
`padded_size`（と任意の `sample_rate`）。道は2つ。

| | 中身 | 値段 | 往復で Y8PC が同じに戻るか |
|---|---|---|---|
| い | 逆コンパイルが Y8PC から JSON と `.bin` を作り、`#pcmbank` でそれを指す | 逆コンパイル側だけ。コンパイラは変えない | **番号が 0 から隙間なく並ぶときだけ。** `entries` の先頭 64 個は必ず既定の番号を取るので、Y8PC の番号に隙間があると（例: 0 と 5 だけ）`#adpcm 5` を足しても既定の 0・1 が残り、設定が増える。鳴らさない番号が増えるだけで、鳴り方は変わらない。**未検証** |
| ろ | `#pcmbank` が Y8PC も読めるようにする（先頭の `Y8PC` で見分ける） | `readAdpcm` の分岐と Y8PC の読み取り、`mml-source.md` の `#pcmbank`、試験 | 設定をそのまま写すので戻る（確認済み。下の「確かめたこと」）。`#adpcm` は Y8PC に名前が無いので使えない |

ろは `#pcmbank` の受け付けるものが増えるので、外に出る値。

#### 障害3: MML が出さない形（乙・丙で出うる）

`y8mmlc` の出力には現れないが、ほかの書き手なら出しうるもの。MML で書けないので、
出会ったらバイト列は同じに戻らない。**推測** ―― 乙・丙の実物で何が出るかは
まだ1件も見ていない。

- 音色集合の順番。`y8mmlc` はトラック A から順に、初めて使った順に索引を振る。
  ROM は `MTRK` を呼んだ順になるはずで、索引がずれる（鳴り方は同じ）
- 名指されない音色レコード、同じ索引の二重書き
- FM で `82` に 0-63（`y8mmlc` は必ず `85` にする）、`83 00`、12 未満の `C0`、
  32 未満のテンポ、音源ごとの範囲を超えた `E0`（`y8mmlc` は断る、ROM は通す）
- `A8` を省く・重ねる位置が `y8mmlc` の規則と違うもの
- トゥコーダとフィーネの到達カウンタ番号が出現順でないもの、`44` が2つあるもの、
  同じ番号のセーニョのうち最後でないものへ飛ぶ `D5`、目印の直後でない所への飛び
- 知らないオペコード（大きさは分かるので読み飛ばせるが、MML にする手段が無い）

セーニョの番号は付け直せば鳴り方は同じにできる。ほかは生のバイト列を書く拡張を
入れない限り戻らない。

#### ついでに見つけた食い違い

**確認済み**（`build/bin/Debug/y8mmlc.exe` に `#assign A SSGS 0` と `A C1.......` を
通した）。付点7つで `00 81 7E`、つまり **382 tick** が出る。`bytecode.md` は
「取りうる最大は複々付点全音符の 336 tick」と書いている。`dots` は付点の数を
制限しない。ROM が付点の数を制限しているかはまだ読んでいない。

#### 値段の見積り（着手前のもの）

| 範囲 | 中身 |
|---|---|
| 甲（ADPCM 無し） | ブロックとイベントを読む、飛び先を組み直す、`#voice` `#wave` `#env` を書く。長さは連符の探索か、長さの拡張1つ。往復の試験は既存の MML から作れる |
| ＋ADPCM | Y8PC を読む（Y8PC の書き手 `writePcmFile` の裏返し）。上の「い」か「ろ」 |
| 丙 | 長さはタイと休符で分ける（上）。1 tick と `~` は残る。ほかは Y8960SeqConverter がループしか出さないなら甲の範囲で済む（**推測** ―― `conversion.md`「繰り返し」がループだけを挙げている） |

#### 作った形（2026-09-27）

- コアは `src/core/decompile.{h,cpp}` の `decompileBlock`。CLI は
  `src/cli/y8mmld.cpp`。**書き出す前に、作った MML を `compileText` に通す。**
  通らなければ何も書かず、`y8mmld` の不具合として報告する ―― 通らない MML を
  渡しても使い道が無いため
- **音色の番号は、トラック A から順に初めて名指された順に振る**（FM は `@128`
  から、SCC は `@16` から）。コンパイラが音色集合を埋める順と同じなので、
  1往復目から番号が動かない
- **`N` の長さは `L` で渡す。** MML の読み手は空白を飛ばして数字をつなげるので、
  `N` の番号の直後に長さの数字を書く手段が無い（`N36` `4` は `N364` になる）。
  長さ 0 は `L` が取れないので `#define Z 0` を出して `=Z;` で書く
- **1 tick は2 tick にして、次に来る時間を取るイベントから1 tick 引く。**
  警告を出す。トラック全体の長さは変わらない
- **書けないものは警告を出して捨てる。** 時間を取るものは同じ長さの休符に置き
  換えて、トラックの長さを保つ
- **楽器を1つも鳴らさないリズムの打撃（`C8 00`）は休符にして警告する。**
  確認済み（`../Y8960Sequencer/src/core/dev_opl2ex.cpp` の `rhythmStrike` を
  読んだ）―― 楽器 0 の打撃もリズムのキーを全部落とす書き込みをするので、何も
  書かない休符とは鳴り方が違う。MML には楽器 0 の打撃を書く手段が無い
- `Y` のレジスタ範囲の検査は `regWritable`（`mml.cpp`）を共有する。2か所に
  書くと片方が古くなるため
- `#pcmbank` は先頭の4バイトが `Y8PC` なら Y8PC として読む。**Y8PC に
  `#adpcm` を足すとエラー**（Y8PC には名前が無い）

#### 確かめたこと

- **確認済み** ―― `tests/decompile_test.cpp`。y8mmlc が出したブロック9種
  （demo、走行状態と音符、ループ・ブロック・記号、SCC 波形、2チップの FM 音色、
  ソフトウェアエンベロープ、リズム、長さ 0 の `N`、空のトラック）が
  **1往復目からバイト単位で戻り**、2往復目で MML も一致する
- **確認済み** ―― 手で組んだ書けない長さのブロック（Q4 の 100 tick と 256 tick、
  Q8 のタイ、休符 33、待ち 37、`N` の 100 tick、Q7 の 8191 tick、リズムの 51 tick）
  で、試験の中の小さな再生器（キーオン・音程・キーオフの位置を tick ごとに追う）が
  元と再コンパイルしたブロックで一致した。**この再生器が違いを捕まえることは、
  Q の書き換えをわざと外して2件落ちるのを見て確かめた**
- **確認済み** ―― `../Y8960Sequencer` の `y8960player --wav`（Release ビルド。
  そのリポジトリの `bb40405` のコミットより後の時刻にビルドされたもの）で、SSGS・OPLLEX の
  FM・OPLLEX のリズムに書けない長さを並べたブロックと、その逆コンパイルを
  コンパイルし直したブロックの WAV が**ビット単位で一致した**。Q の書き換えを外して
  タイだけでつないだ MML では WAV が変わることも見た
- **確認済み** ―― ADPCM の曲を Y8PC 付きで往復させ、Y8SQ も Y8PC もバイト単位で
  戻った。Y8PC が無ければ断る
- **確認済み** ―― CLI（`tests/cli_test.cpp`）。既にある `.mml` を断る、
  `--force` で上書きする、同じ茎の `.PC` を拾う。ASCII でない名前のフォルダで
- **未検証** ―― ROM の `MSAVE` が出したブロックはまだ1つも通していない

#### Y8960SeqConverter の出力で確かめたこと（2026-09-27）

Y8960SeqConverter が MuSICA と OPLLDRV の演奏データから作ったブロック 79 本
（手元のデータ。権利の都合でどのリポジトリにも置かない）を、逆コンパイル →
コンパイル → 逆コンパイル → コンパイルし、元と1往復目を `y8960player --wav` で
比べた。**確認済み**（走らせた）。

| | 本数 |
|---|---|
| 逆コンパイルできた | 78 |
| 2往復目で MML もブロックも変わらない | 78（全部） |
| WAV がビット単位で一致 | 48 |
| WAV が違う | 30 |
| コンパイルできない MML になった（分けた結果トラックが 2048 バイトを超えた） | 1 |

WAV が違う 30 本の原因は2つで、**それぞれ確かめた**。

- **リズムのアクセント（30 本すべて）。** 元のブロックは叩かない楽器にも `A8` の
  ビットを立てている（例: `A8` がバスドラムを指したままハイハットだけを叩く）。
  MML の `!` は叩く楽器にしか付かないので、コンパイルし直すと `A8` が叩く楽器
  だけに絞られる。**再生器は打撃のたびに5つの楽器すべての音量を `A8` から書き
  直す**（`../Y8960Sequencer/src/core/dev_opllex.cpp` の `rhythmStrike` と
  `writeRhythmLevels` を読んだ）ので、鳴り続けている楽器の減衰が変わる。
  確かめ方: トラックを1本ずつ鳴らすと違うのはリズムのトラックだけで、コンパイルし
  直したブロックの `A8` の値だけを元の値に書き戻すと、警告の無い曲の WAV は一致した
  （3曲で試した）。30 本全部で書き戻すと 9 本が一致し、残る 21 本は次の原因も持つ
- **1 tick（残る 21 本すべて）。** 1 tick の長さは 21 本に 1287 個あり、うち
  1204 個が音符。多くは `Q` の変更に挟まれていて、変換元の書き方として普通に
  出てくる形。アクセントを書き戻したあとも違いが残る 21 本は、どれも 1 tick の
  警告が出た曲だった（1 tick の警告が無くて違いが残る曲は無かった）
- `Q` をループの向こうから仮定した警告（3本、275 個）は、それだけが出た曲の WAV が
  一致した。仮定が外れた例はまだ見ていない
- リズムの待ち（`0E`）を休符にするのは鳴り方を変えない。元のブロックの `0E` を
  `0C` に書き換えて WAV が一致した（3曲）。いまはリズムにも `@W` があるので、
  `0E` はそのまま `@W` に戻す

**アクセントの落ちは、いまは警告を出す**（トラックごとに1回、落ちた打撃の数を
添えて）。見つける前は黙って落としていた。

#### 残っていること

- **1 tick の音符・打撃**は1 tick ずれる（警告が出る）。Y8960SeqConverter の
  出力では珍しくないと分かった（上）。**見送った「tick 数をそのまま書く長さ」を
  読み直す条件に当たった。** 入れれば分割が要らなくなり、トラックが 2048 バイトを
  超える問題も消える。**それでも見送った**（利用者の判断、2026-09-28）。理由:
  1 tick のずれは聴いてほとんど分からない。前提: 聴いて分かる曲が出るか、
  トラックが 2048 バイトを超えて逆コンパイルできない曲が問題になれば読み直す
- **叩かない楽器へのアクセント**は MML で書けない（警告が出る）。MML に書き方を
  足す案と、`A8` の叩かない楽器のビットに意味を持たせないと ROM・Y8960Sequencer・
  Y8960SeqConverter の側で決める案があったが、**どちらも見送った**（利用者の判断、
  2026-09-28）。理由: 聴いてほとんど分からない。前提は上と同じ
- **`~` の付いた、書けない長さの音符**は、分けた最初の1片で音程の移動が終わる
  （警告が出る）
- **ループやジャンプをまたいで `Q` が違う値になりうるところ**では、並びの上で
  直前の `Q` を仮定して分ける（警告が出る）。推測 ―― Y8960SeqConverter は
  ループの本体が周ごとに同じバイト列のときだけループにするので、出にくい
- 分けた長さは `7....` のような読みにくい形になることがある。付点の少ない順に
  選んでいるだけで、よく使う分母を優先してはいない

## 見送った案

### ROM の Z80 コードを走らせて MML をコンパイルする

`MTRK` をエミュレータの中で呼び、`MSAVE` の結果を取り出す案。ROM と同じ
バイト列になることが構造上保証される。

見送った理由:
- MSX エミュレータと ROM イメージの配布が要る。ROM には他の拡張BASIC と、
  出典の違う音色データが含まれる
- 要件はマルチプラットフォームのコマンドラインツールで、そこに MSX の
  エミュレータを抱えることになる
- Y8960Sequencer が同じ理由で同じ案を見送っている

### 再生追従とシーク（見送った。調べた結果は残す）

利用者の決定（2026-09-18）。**再生位置に追従したソース行のハイライトと、
カーソル位置からの再生は要らない。** 決める前に何が要るかを調べたので、
**後で欲しくなったときに調べ直さずに済むよう**、分かったことを残す。

#### tick ↔ ソース行の表は作れない

これが調べて分かったいちばん大きなこと。**流用できると思った前例の形が、
ここでは成り立たない。**

- `../mml2mid64ide` で tick → 行が成立するのは、**SMF がループを展開した
  線形の列**だから。コンパイル時に「この tick はこの行」が静的に決まる
- **Y8SQ は展開しない。** `|:` `:|` `[n` `(DC)` `(DS)` `(TC)` はジャンプとして
  残り、プレイヤーが実行する（`bytecode.md`「飛び先の書き方」）。同じソース行が
  何度も違う tick で鳴り、**どの tick がどの行かは実行時のループ回数で決まる**
- 静的に決まるのは **(トラック番号, イベント列のバイト位置) → ソース行** のほう。
  こちらのコンパイラはイベントを出す時点で両方を持っているので、表を作るのは安い

#### 報告するのは tick ではなく `Track::ptr`

**確認済み**（`../Y8960Sequencer/src/core/sequencer.h` と `timing.h` を読んだ）。

- **200Hz は tick の速さではなく割り込みの速さ。** tick は割り込みごとに
  `TickIncrement{whole, frac/65536}` ずつ進む。四分音符 48 tick・T120 なら
  毎秒 96 tick なので、1割り込みあたり約 0.48 tick
- **4シーケンスが別々のテンポで進む**ので、「その曲の tick」は1つではない
- **絶対 tick カウンタは無い。** `Sequence` が持つのは 16bit の `acc` だけ
- **`Track::ptr`（イベント列の中の現在位置）は既にある。** 報告するならこれで、
  新しい状態を持たなくてよい

#### 音声バッファのぶん、位置は先行する

`mmlplay` には無い問題。あちらは MIDI を実時間で送るので「送った＝鳴った」。

- `PlaybackEngine::render()` は SDL のコールバックから呼ばれて**先の時間ぶんを
  作り置きする**（`../Y8960Sequencer/src/app/engine.cpp` の `feed`）。素直に
  位置を読むと、まだ鳴っていない行を指す
- 直すなら、位置をサンプル位置と組で記録し、`SDL_GetAudioStreamQueued()` を
  引いた地点を引き当てる。**未検証** ―― 実際の先行量は測っていない

#### シークは復元できない

MIDI ならコントローラの最終値を送り直せば復元できるが、こちらは**チップの
レジスタ・エンベロープ・ループカウンタ・到達カウンタ**が全部状態になる。
正しくやるには先頭から無音で走らせ直すしかない。

### ADPCM のエンコードもこのツールで行う

要件は「adpcm_packer が出力したダンプと JSON」を入力に取ると定めている。
**符号化は adpcm_packer の仕事**で、こちらはその出力を Y8PC の形に詰め替える。

#### 256 バウンダリに詰め直した（2026-09-19）

最初に置かれたバンクは `boundary` が 32 で、36 エントリ全部が 256 の境界に
載っておらず、`#pcmbank` が受け付けなかった（`pcmfile.md` はページを 256 バイトと
定める。**コンパイラ側を緩める話ではない** ―― 緩めると音源が読めない配置の
ファイルができる）。パラメータの `boundary` を 256 にして作り直した。

**詰め直す前に、元のバンクを再現できることを確かめた**（確認済み）。

- パラメータの 36 本のうち 2 本（`PSS-590_OrchestraHit` と `PSS-590_Timpani`）は
  元の作業場所の `banks/PCM/common/_fixed_source/` を指していた。`presets/wavs/
  melodic/` に同名のファイルがあるが、**そちらは 8bit PCM で adpcm_packer が
  受け付けない**（走らせて確かめた）。`_fixed_source` はその 16bit 版で、
  `../FITOM_staging/banks/PCM/common/_fixed_source/` にあった
- その2本を使うと、boundary 32 のまま**元の `.bin`（95360 バイト）がバイト単位で、
  `.json` も完全に一致した**。パラメータとソースの組が正しいことの証拠になる
- **利用者が `presets/wavs/melodic/` の2本を 16bit 版に置き換えた**（2026-09-19）。
  `_fixed_source` の2本と SHA-1 まで同じであることを確かめ、パラメータのパスを
  `wavs/melodic/` に戻した。作り直したバンクはコミット済みのものと同一だった。
  出力先は `presets/` の中の同じ名前に向けてある。**`presets/` をカレントにして
  `adpcm_packer params_y8950_adpcmb_excerpt.json` を走らせると、コミットした
  バンクがそのまま出る**。ただし `wavs/` はリポジトリに入らないので、
  **作り直せるのは録音の元ファイルを持っている利用者の手元だけ**

**詰め直した結果**（確認済み）。boundary 256、36 エントリ、99584 バイト
（389 ページ）。256 の境界に載らないエントリは 0。**各エントリの符号化データは
boundary 32 版とバイト単位で同一**で、動いたのは配置だけ（音は変わっていない）。
詰め物はすべて 0x00。36 本すべてを既定の番号 0-35 で鳴らす曲を `y8mmlc` に通し、
Y8PC の設定 36 件・Y8SQ のチャンク 03 が 36 件になり、Y8960Sequencer の
`y8960player` が「ボイスファイル 36 個」で受理した

### 検証をどこまでやるか

**いちばん強い検証は、同じ MML を ROM と このコンパイラの両方に通して
バイト列を突き合わせること。** ROM 側は openMSX のフォークでしか回せないので、
このリポジトリからは回せない。いまの代わりは2つ。

- ROM の `doc/plan.md` が持つ実例を期待値に写した回帰試験（`tests/mml_test.cpp`
  の「ROM:」と書いてある行）。**写した実例は上の表が持つ**
- **出力を Y8960Sequencer に読ませる。** 向こうは同じ仕様から独立に書かれた
  読み手なので、こちらの書き手の取り違えを捕まえる見込みがある

足すなら、ROM 側に「MML を食わせて `MSAVE` の結果を吐く」試験スクリプトを
置いてもらい、その出力をこちらの試験データにする。

**この検証を見送っている間、互換性の根拠は「仕様文書と ROM のコードを読んで
実装し、独立の読み手が受理した」までである。** ROM と同じ音が鳴ることは
確かめていない。`README.md` には書かない（利用者向けの文書に開発の都合は
書かない）代わりにここに書く。
