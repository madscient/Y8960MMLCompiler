# 依頼：Y8960 MML 用の VS Code 拡張を作る

**この文書は、VS Code 拡張の新しいリポジトリで最初に作業するセッションへの
依頼書。** 書いたのは Y8960MMLCompiler（MML コンパイラ `y8mmlc`）のリポジトリ
で作業したセッション。役目を終えたら、このリポジトリから削除する。

以下の相対パスは、**拡張のリポジトリが Y8960MMLCompiler と同じ親フォルダに
並んでいる**ことを前提にしている。違う場所にあるなら読み替えること。

## 何を作るか

Y8960 カートリッジの MML を書くための VS Code 拡張。コンパイルは既存の
コマンドラインツール `y8mmlc` に任せ、拡張は**編集の場**を受け持つ。

- `.mml` の構文強調（文法はコンパイラのリポジトリから受け取る。下記）
- 保存時またはコマンドでのコンパイルと、エラーの一覧・行ジャンプ
- できたシーケンスを `y8960player` で鳴らす

## 決まっていること（利用者の決定）

- **拡張は Y8960MMLCompiler とは別リポジトリ。** 向こうは C++/CMake、こちらは
  TypeScript/npm/VSIX で、技術スタックと配布経路を混ぜないため
- **コンパイラ側に GUI は作らない。** 編集の場はこの拡張だけ
- **再生位置に追従したソース行のハイライトは要らない。シークも要らない。**
  どちらも見送り済み。理由と調べた結果は `../Y8960MMLCompiler/doc/plan.md` の
  「再生追従とシーク」にある（Y8SQ はループを展開しないので、tick からソース行を
  静的に引く表が作れない）。**着手前に掘り返さないこと**
- したがって**プレイヤーとの間にプロトコルは要らない。** `y8960player` を子
  プロセスとして起動し、止めるときは終了させる

## 境界：拡張が頼ってよいのは CLI だけ

拡張は `y8mmlc` の **C++ の API ではなく、引数・終了コード・出力の書式**に
依存する。向こうの `doc/plan.md` がこれを「外から見える値」として扱うと
決めている。以下は 2026-09-19 に `y8mmlc` を走らせて確かめた値。
**古くなっているかもしれないので、使う前に同じことを自分で走らせて確かめる。**

### `y8mmlc`

```
y8mmlc <MML ソース> [-o <基底名>] [--out-dir <フォルダ>]
```

| 終了コード | 意味 |
|---|---|
| 0 | 成功 |
| 1 | コンパイル失敗（何も書き出さない） |
| 2 | 引数の誤り |

**診断は stderr に1行ずつ。** 形は3通りある。

```
<パス>:<行>:<桁>: error: <文面>
<パス>:<行>: error: <文面>
<パス>: warning: <文面>          ; 行を指さないもの
```

- 行と桁は 1 から数える。**桁は UTF-8 のバイト数**（確認済み ――
  `#voice 128 "あ", zz` の `zz` を 19 桁目と報告する。文字で数えれば 17）。
  VS Code の桁は UTF-16 なので、**多バイト文字を含む行では拡張の側で直す**。
  MML の中に多バイト文字が来るのは `"..."` の中くらいだが、起きうる
- **並びは固定、文面は変わりうる。** 文面を解析しないこと
- 失敗したときは最後に `y8mmlc: <N> error(s); nothing was written` が付く
- **成功したときは、書いたファイルが stdout に1行ずつ**出る：
  `<パス> (<バイト数> bytes)`

**出力ファイル**は `<基底名>.SQ`（シーケンス）と、ソースに `#pcmbank` がある
ときだけ `<基底名>.PC`（ADPCM）。基底名は入力の茎を大文字にして 8 文字に
切ったもの（切ったときは警告が出る）。置き場所は既定でソースと同じフォルダ。

**1回の実行で全部の誤りが出るわけではない**（そういう仕様。利用者の決定）。
メタコマンドの段で誤りがあると、MML の解析まで進まずに終わる。直して
走らせ直すと次の誤りが出る。

### `y8960player`（`../Y8960Sequencer`）

```
y8960player <シーケンスファイル> [--adpcm <ADPCM ファイル>] [--tick <0-2>]
```

- エミュレータの共有ライブラリ3本を**実行ファイルと同じフォルダ**に置く必要が
  ある（向こうの `README.md`）
- 位置を報告する口は無い。鳴らして、終われば終了する

### 構文強調は作らずに受け取る

**TextMate 文法はコンパイラのリポジトリにある**
（`../Y8960MMLCompiler/syntaxes/y8960mml.tmLanguage.json`）。この拡張で書き起こさ
ないこと。文法を直したくなったら、コンパイラのリポジトリへの依頼にする ――
メタコマンドを足したときにずれないよう、向こうの試験がパーサと文法を突き合わせて
いる。

- **受け取り方（submodule、ビルド時に写す、リリースから取るなど）は、この
  リポジトリで決める**（利用者の決定）。着手前に利用者に聞く
- 文法はリズム音用 MML のトラックも普通の MML として色付けする。どのトラックが
  リズムかは `#assign` のチャンネルで決まり、TextMate 文法には見えない。それ以上を
  望むなら、拡張の側で `#assign` を読んで色を足すことになる（semantic tokens など）
- **VS Code 本体で色付けを確かめてはいない。** 向こうでは Oniguruma に通した
  簡易トークナイザで確かめただけなので、この拡張で最初に確かめること

## 決まっていないこと ―― 着手前に利用者に聞く

**どれも外から見える値で、後から変えると波及する。** 実装順の都合で決めて
しまわないこと。

- **拡張の名前・publisher・言語 ID。** 前例の `../mml2mid64ide` の拡張が
  言語 ID `mml` で `.mml` を登録している（確認済み）。**両方を入れると `.mml` を
  取り合う。** 別の言語 ID にするか、拡張子を変えるか、共存をどう扱うか
- **`y8mmlc` と `y8960player` の見つけ方。** 設定でパスを持つか、PATH から探すか、
  拡張に同梱するか（同梱ならエミュレータの共有ライブラリ3本も要る）
- **TextMate 文法の受け取り方。** submodule、ビルド時に写す、リリースから取る、など
- **コンパイルの契機。** 保存のたびか、コマンドだけか
- **出力の置き場所。** ソースの隣（`y8mmlc` の既定）か、作業用フォルダか
- **診断を機械可読にするか。** いまはテキストの3形式を読むことになる。
  `--diag=json` のような出力が欲しいなら、コンパイラ側への依頼になる（下記）

## やってはいけないこと

- **Y8960MMLCompiler・Y8960Sequencer・Y8960BasicExtension を編集しない。**
  コンパイラやプレイヤーに足してほしいものが出たら、**向こうのリポジトリで
  作業するセッションに渡す依頼文を書いて利用者に渡す。** 向こうの作業ツリーは
  別のセッションが編集していることがある
- **`y8mmlc` の診断の文面に依存しない。** 並びだけを読む

## 前例について

`../mml2mid64ide` は同じ形（MML コンパイラ ＋ VS Code 拡張）の先行プロジェクトで、
`extension/` に言語登録・TextMate 文法・診断の骨格がある。**流用してよいが、
前提が違う**ことに注意する。

- あちらはコンパイラを WASM で同梱し、`--diag=json` とデバッグマップを使う。
  **こちらの `y8mmlc` にはどれも無い**
- あちらの拡張はロードマップのマイルストーン1 の途中（再生同期の手前）で
  止まっている。こちらは再生同期を持たないので、そこまでは要らない
